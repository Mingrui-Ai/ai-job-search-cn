# M2-5 第二轮操作清单

M2-6 做完以后，M2-5 第二轮在用户的真实岗位和档案上重新评一次分，由用户逐个岗位确认认可与否（见[路线图](roadmap.md)的 M2-5）。本文写操作步骤：用 cn-setup 补档案的哪几项、每项怎么问怎么填，以及重新导入、补档案、重新评分、调权重、出报告的顺序和命令。

底本是 M2-6d 工作记录（[2026-10-30-m2-6d-weights.md](worklog/2026-10-30-m2-6d-weights.md)）里的草稿：Codex B 用示例数据演练过一遍（V20），提的三处已在 #76、#87 改好。本文补上 M2-6e（薪资分档）和 M2-6f（去外地面试的偏好）。

**隐私**：本文只写字段和做法。用户的回答（薪资的各个数、城市、愿不愿意去外地面试）只写进本机数据目录里的档案和 `notes.md`，不写进仓库的文档、测试、提交说明和 PR。下文的 `<金额>`、`<城市>` 都是占位，不是建议的值。

## 顺序

**先重新导入岗位，再补档案，再全部重新评分、补经历，最后调权重。**

- 岗位重新导入（会补上新字段、按新规则重读）以后，或者档案的内容（薪资、城市、面试偏好等）改了以后，旧记录就过期了。重新评分生成的新草稿里，Agent 原来补的经历和方向是空的，要重新核对、补上。
- 只改权重时，重新评分会保留这些判断。所以会让判断作废的两步放在补经历之前，调权重放在最后。顺序反过来，补过的经历要再补一遍。
- M2-6 期间评分规则的版本（`rules_version`）升了几次，第一轮保存的记录本来就都会过期（`stale_reasons` 里有 `rules`），这一轮每个岗位都要重新补经历。

## 前提

- M2-6c、M2-6d、M2-6e、M2-6f 都已合并；
- 由 Codex A 在自己的工作树里用最新的 master 做（规划者 2026-10-30），用户回答问题、确认档案和结论；
- 在 conda 环境 `ai-job-search-cn` 里运行。

## 先定数据目录

只给命令加 `--data-dir` 不够，Agent 手工读写的文件也要用同一个目录（V20 演练发现，建档和评分工作流的开头已写明）。下面的 `<数据目录>` 是主工作树的 `data`：

- 所有命令都加 `--data-dir <数据目录>`，下文省略；
- Agent 手工读写的文件都用完整路径，工作流里写的 `data/...` 在这里都是 `<数据目录>/...`：
  - 档案：`<数据目录>/profile/profile.json`；
  - 笔记和偏好记录：`<数据目录>/profile/notes.md`；
  - 评分草稿：`<数据目录>/matches/drafts/<岗位id>.json`；
  - 报告和反馈表：`<数据目录>/reports/<日期时间>/`；
  - 第 1 步导出的原文：`<数据目录>/inbox/reimport/<岗位id>.txt`；补全字段时写出的整条记录：`<数据目录>/inbox/<岗位id>.json`。岗位库在 `<数据目录>/jobs/`，只通过 `jd` 命令改，不手工写。
- 不要改执行这份清单的 Agent 自己工作树里的 `data/`：那是另一份数据，改了以后，校验的还是 `<数据目录>` 里的。

## 步骤

1. **重新导入已保存的岗位**（走 [JD 导入工作流](jd-import.md)）。以前保存的岗位，后来加的字段读出来是 null（M2-6c 的面试形式和到岗时间，M2-6e 的包餐），规则读出的字段也要按新规则重读（例如 H21 的版本号写法）。重新导入以后才会读出来：
   - `python -m jobsearch_cn jd list` 列出已保存的岗位；
   - 对每个岗位，先用 `jd show <id>` 取出 `raw_text`，用写文件的工具存成 `<数据目录>/inbox/reimport/<id>.txt`（UTF-8，不要用 PowerShell 的 `>`）。记录里取不回原文时，用用户保存的原文件；
   - 运行 `jd parse <数据目录>/inbox/reimport/<id>.txt --save`。同一份原文会按 H10 的规则合并进原记录：规则新读出的字段补上，Agent 和用户改过的值保留，`source` 不变；
   - 核对：输出里 `saved[0].action` 应是 `updated` 或 `unchanged`，`id` 和原来一样。出现 `created`（新的 id），说明原文对不上，停下来告诉规划者，不要删除旧记录；
   - 用 `jd show <id>` 看 `interview`、`requirements.start`、`requirements.days_per_week`、`salary` 和 `benefits.meals` 读出了什么。薪资分档要用到后三项：每周天数用于按天和按月互相折算，包餐折成钱加进薪资。原文写了、规则没读到或读错的，按 JD 导入工作流第 3 步补或改，包餐的取值见 [job-schema.md](job-schema.md#包餐和餐补)；原文没写的保持 null。
2. **只诊断档案**：运行 `python -m jobsearch_cn profile validate`。第一轮的档案缺 M2-6 以后加的键，预计报：
   - M2-6e 的五个键都报 missing：`target.salary_ideal`、`target.salary_step`、`target.meal_value`、`target.salary_days_per_week`、`target.one_meal_points`；
   - 第一轮以后没补过的，还会报 M2-6b 的 `availability.acceptable_cities: missing`；自己写过 `weights` 的，还会报 `target.weights.location: missing`；
   - M2-6f 的 `availability.interview_travel` 可以不写，不会报。

   这些是旧格式的错误，下一步补上。在那之前 `match list`、`match score` 都会报 `the profile is invalid`，这不是操作失败，也不要因此删除记录。
3. **补档案**（对 Agent 说"更新档案"，走[建档工作流](profile-setup.md)，改的是 `<数据目录>/profile/` 下的文件）。建档工作流不覆盖已确认的内容，这一轮只问下面几项，以及别的还空着的项。`availability`、`target` 没有 `source` 字段，不要自己加；每改一项，在 `notes.md` 的"偏好记录"追加一条：日期、字段、新的值、来源（格式见 [profile.md §4](profile.md#4-notesmd)）。
   - **最低薪资**（`target.salary_min`）：先确认第一轮写的还对不对。
     - 问："能接受的最低薪资是多少？按天算还是按月算？"
     - 填：`{"amount": <金额>, "unit": "CNY/day"}`。实习一般按天（`CNY/day`），按月写 `CNY/month`。不要按小时：按小时的不换算，也不分档，用户习惯按小时说的，请用户换成按天或按月的数。
     - 告诉用户：不分档时，只和单位相同的 JD 比较，JD 写的上限达到最低期望记 100，达不到记 0。
   - **薪资分档**（M2-6e，`target` 的五个键，规则见 [match.md](match.md#薪资分档m2-6e)）：
     - 先说明：不分档时，薪资只有 0 和 100 两档。分档以后，在最低期望和理想之间记 50，高于理想每多一个步长加 10 分，低于最低期望每差一个步长减 10 分，按比例算，截在 0 到 100；JD 写区间时取最低的数，按天和按月会互相折算，包餐也折成钱加进去。再问用户要不要分档。
     - 不要分档：五个键都写 `null`，评分和以前一样。
     - 要分档，逐项问：

       | 字段 | 怎么问 | 怎么填 |
       | --- | --- | --- |
       | `salary_ideal` | "理想的薪资是多少？"单位和最低薪资一样 | `{"amount": <金额>, "unit": …}`，单位同 `salary_min`，不低于最低薪资 |
       | `salary_step` | "比理想多（或者比最低少）多少钱，算差了一档？"告诉用户：差一档加（减）10 分，高出理想五档到 100 分，低于最低五档到 0 分 | 正数，单位同理想薪资，只写数字 |
       | `meal_value` | "包两餐、三餐，或者只写了'包吃'，对你来说值多少钱？按天还是按月？" | `{"amount": <金额>, "unit": "CNY/day"}` 或 `"CNY/month"`；不想算钱就写 `null` |
       | `salary_days_per_week` | "JD 没写每周几天时，按每周几天折算？"通常就是每周能到岗的天数（`availability.days_per_week`），问用户是不是就按这个数 | 大于 0、不超过 7 的数，可以带小数；说不清就写 `null`，JD 写了每周几天的照样能折算 |
       | `one_meal_points` | "只包一餐（例如只提供午餐）时，加几分？" | 0 到 100 的数；不加分就写 `null` |

     - 理想和步长要么都写，要么都写 `null`，只写一个 `profile validate` 会报错。用户给的是区间时，问清取哪个数，不要自己取。
   - **意向城市的两档**（M2-6b）：
     - 问：先确认首选城市（`availability.cities`）；再问"首选以外，还有哪些城市也可以接受？"
     - 填：`availability.acceptable_cities` 是城市名的列表，例如 `["<城市>"]`；没有就写 `[]`。首选城市不要再写进这一档，`profile validate` 会报错。
     - 告诉用户：两档都算能投；地点分首选城市 100，可以接受的城市 60，其他城市愿意去 30、不愿意 0（见 [match.md](match.md#地点偏好m2-6b)）。
   - **远程和去其他城市**（`availability.remote_ok`、`relocate`）：还空着的必须问到，填 `true` 或 `false`，并告诉用户留空的后果（见建档工作流第 4 步）。
   - **到岗日期**（`availability.start_date`）：M2-6c 的到岗时间检查要用，没填的补上。
   - **去外地面试**（M2-6f，`availability.interview_travel`）：
     - 问："JD 写要到意向城市以外的地方现场面试、没说能线上面试的，你愿意去吗？"
     - 填：愿意写 `true`，暂时不去写 `false`，没想好写 `null`。这个键可以不写，不写和 `null` 一样；问过以后就写上，偏好记录里记一条。
     - 告诉用户：写了 `false`，只在外地现场面试、没有线上选项的岗位会列为待确认，提示投之前先问能不能线上面试，不会被排除；`true` 或没说时照旧，只附上路费和时间成本的提示。能线上面试的、有一个面试地点在意向城市内的、JD 没写面试地点的岗位都不受影响。
   - **自己写过权重的**（`target.weights`）：先补上 `"location"`（写 0 就和以前一样），或者改回 `null`，第 5 步再调。
   - 最后 `profile validate` 要通过。通过以后运行 `python -m jobsearch_cn match list`：旧记录全部过期，`stale_reasons` 里可能有 `job`、`profile`、`weights`、`rules`（V20 演练里四种原因都有）。
4. **全部重新评分，补经历**（对 Agent 说"给已保存的岗位重新评分"，走[评分工作流](match.md#评分工作流三个-agent-共用)第 2–5 步）：
   - 每个岗位：`match score <id> --draft` → 在新草稿里重新核对、补上经历（草稿里 Agent 原来的判断是空的）→ `match validate <数据目录>/matches/drafts/<id>.json` → 抄 `total` → `match save <数据目录>/matches/drafts/<id>.json`；
   - 保存成功后才替换旧的匹配记录，在那之前旧记录都还在；
   - 向用户说明时（工作流第 6 步），薪资分了档的，照理由讲出折算过程：区间取了最低的多少、按谁的每周几天折算、包餐加了多少、落在哪一档；面试一项判待确认的，讲清是因为只在外地现场面试，而用户暂时不去外地面试；
   - 做完以后，`match list` 里不应再有 `stale` 的记录。
5. **调权重**（对 Agent 说"我现在更看重……"，走评分工作流的"评一批岗位前：先问现在看重什么"）：
   - Agent 换算成合计 100 的五项，用 `match list --weights skills=…,direction=…,experience=…,salary=…,location=…` 试算，给用户看百分比和排序的变化。在 Windows PowerShell 5.1 里，`--weights` 后面不加引号也能整个传进去；
   - 用户看了试算只改其中几项的（例如"把薪资和地点提到 20"）：这几项照用户的数，其余几项按用户正在改的那组试算的占比分摊剩下的，不留在试算的数上、也不把差额都给一项；用户说某项"不变"的才保持原数（见评分工作流"换算规则"第 1、3 步和"在试算上接着改"的例子）；
   - 用户明确确认后，写 `target.weights`、在偏好记录追加一条，再跑 `profile validate`；
   - 不想调就跳过这一步。
6. **只因权重过期的记录重新评分**：`match list` 里 `stale_reasons` 只有 `weights` 的，逐个运行 `match score <id> --save`。经历会保留，每个几秒钟。做完以后，`match list` 的排序和第 5 步的试算一致。
7. **出报告、填反馈**：
   - 运行 `match report`（不写 id 时包括所有已保存的记录）。输出的 `stale` 不为空时，先把这些记录重新评分，再生成；
   - 用浏览器打开 `report.html`，用 Excel 或 WPS 打开 `feedback.csv`，填好"你的等级""认可""原因"三列，保存时保持 CSV（UTF-8）格式；
   - 报告的待确认事项里有 M2-6e、M2-6f 的提示：薪资算不出来时怎么确认（面议、按小时、缺每周天数），只在外地现场面试的岗位提示"问 HR 能不能线上面试"；
   - 告诉 Agent 填好了，由它汇总认可的情况（评分工作流第 6 步的"报告和反馈表"）。
8. **交给规划者**：按第一轮的做法（[汇总记录](worklog/2026-10-29-m2-5-trial.md)），真实岗位、档案、匹配记录和反馈表只留在本机的 `<数据目录>`，工作记录只写汇总。薪资只写落在哪一档、认可与否，不写用户的最低期望、理想、步长、包餐折合多少和每周几天。用户觉得结论不对、对规则有意见的，原样转告规划者，不要手改记录或规则。
