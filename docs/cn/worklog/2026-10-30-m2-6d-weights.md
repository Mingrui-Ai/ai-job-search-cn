**决策**

- 换算规则最初只改用户提到的维度，没提到的数字不动，理由是 V14 要看"相对默认权重调高、调低还是不变"，按比例重新分配成 100 会让没提到的数字也变小。V14 的对照（#77）发现这样不对，规划者已经改了裁定，见下一节。
- 最初的换算按顺序做：先降"不太在乎"的，再升"其次"的（不调高的各项里最大的数 + 5），最后升"最看重"的（其余各项里最大的数 + 10）。
- "只说不想要什么"先问清是硬性条件还是偏好：硬性的（看到就不投）改 `relocate`、`exclusions`、`salary_min`，按建档工作流改；能投但排后面的才是权重。
- 说的不是这五项的（大厂、转正、成长）不硬套进某一项。
- 报告不显示试算：报告和反馈表是让用户对已保存的结论表态的，混进试算的总分，就分不清哪个是真的。
- `cn-match` 原来只允许写草稿。新的一步要在用户确认以后写档案的权重和偏好记录，所以两个入口写明这一例外；硬性条件的字段仍按建档工作流改。

**M2-5 第二轮的操作清单（草稿，规划者 2026-10-30 要的）**

**顺序很重要：先重新导入岗位，再改档案内容，再全部重新评分、补经历，最后调权重。** 岗位内容（重新导入会补上新字段）和档案内容（薪资、城市等）一改，旧记录就过期了；重新评分生成的新草稿里，Agent 原来的判断是空的，要重新核对、补上。只改权重时，重新评分会保留这些判断。所以会让判断作废的两步放在补经历之前。

前提：
- M2-6c、M2-6d 都已合并；
- 第二轮由 Codex A 在自己的工作树里用 master 的代码做（规划者 2026-10-30）；
- 在 conda 环境 `ai-job-search-cn` 里运行。

**先定数据目录**（V20 演练发现：只给命令加 `--data-dir` 不够，手工读写的文件也要用同一个目录）。下面的 `<数据目录>` 是主工作树的 `data`：
- 所有命令都加 `--data-dir <数据目录>`，下文省略；
- Agent 手工读写的文件都用完整路径，建档和评分工作流里写的 `data/...` 在这里都是 `<数据目录>/...`：
  - 档案：`<数据目录>/profile/profile.json`；
  - 笔记和偏好记录：`<数据目录>/profile/notes.md`；
  - 评分草稿：`<数据目录>/matches/drafts/<岗位id>.json`；
  - 报告和反馈表：`<数据目录>/reports/<日期时间>/`；
  - 第 1 步导出的原文：`<数据目录>/inbox/reimport/<岗位id>.txt`。岗位库在 `<数据目录>/jobs/`，只通过 `jd` 命令改，不手工写。
- 不要改执行者自己工作树里的 `data/`：那是另一份数据，改了以后，校验的还是 `<数据目录>` 里的。

1. **重新导入已保存的岗位**（走 JD 导入工作流）。M2-6c 以前保存的岗位，面试形式和到岗时间读出来是 null，重新导入以后规则才会读出来：
   - `python -m jobsearch_cn jd list` 列出已保存的岗位；
   - 对每个岗位，先用 `jd show <id>` 取出 `raw_text`，用写文件的工具存成 `<数据目录>/inbox/reimport/<id>.txt`（UTF-8，不要用 PowerShell 的 `>`）。记录里取不回原文时，用用户保存的原文件；
   - 运行 `jd parse <数据目录>/inbox/reimport/<id>.txt --save`。同一份原文会按 H10 的规则合并进原记录：规则新读出的字段补上，Agent 和用户改过的值保留，`source` 不变；
   - 核对：输出里 `saved[0].action` 应是 `updated` 或 `unchanged`，`id` 和原来一样。出现 `created`（新的 id），说明原文对不上，停下来告诉规划者，不要删除旧记录；
   - 用 `jd show <id>` 看 `interview` 和 `requirements.start` 读出了什么。
2. **只诊断档案**：运行 `python -m jobsearch_cn profile validate`。预计报 `availability.acceptable_cities: missing`；自己写过 `weights` 的，还会报 `target.weights.location: missing`。这些是旧格式的错误，下一步补上。在那之前 `match list`、`match score` 都会报 `the profile is invalid`，这不是操作失败，也不要因此删除记录。
3. **补档案内容**（对 Agent 说"更新档案"，走建档工作流，改的是 `<数据目录>/profile/` 下的文件）：
   - `target.salary_min`：最低期望薪资。实习按天填（`CNY/day`），和 JD 的单位一致才能比较；
   - `availability.acceptable_cities`：可以接受、但不是首选的城市，没有就填 `[]`；
   - `availability.remote_ok`、`relocate`：还空着的补上；
   - `availability.start_date`：M2-6c 的到岗时间检查要用，没填的补上；
   - 自己写过 `weights` 的：先补上 `"location"`（写 0 就和以前一样），或者改回 null，第 5 步再调；
   - 每改一项，Agent 在 `notes.md` 的"偏好记录"记一条；
   - 最后 `profile validate` 要通过。通过以后运行 `python -m jobsearch_cn match list`：旧记录全部过期，`stale_reasons` 里可能有 `job`、`profile`、`weights`、`rules`（V20 演练里三条记录四种原因都有）。
4. **全部重新评分，补经历**（对 Agent 说"给已保存的岗位重新评分"，走评分工作流第 2–5 步）：
   - 每个岗位：`match score <id> --draft` → 在新草稿里重新核对、补上经历（草稿里 Agent 原来的判断是空的）→ `match validate` → 抄 `total` → `match save`；
   - 保存成功后才替换旧的匹配记录，在那之前旧记录都还在；
   - 做完以后，`match list` 里不应再有 `stale` 的记录。
5. **调权重**（对 Agent 说"我现在更看重……"，走评分工作流的"评一批岗位前"）：
   - Agent 换算成合计 100 的五项，用 `match list --weights …` 试算，给用户看百分比和排序的变化；
   - 用户明确确认后，写 `target.weights`、在偏好记录追加一条，再跑 `profile validate`；
   - 不想调就跳过这一步。
6. **只因权重过期的记录重新评分**：`match list` 里 `stale_reasons` 只有 `weights` 的，逐个运行 `match score <id> --save`。经历会保留，每个几秒钟。做完以后，`match list` 的排序和第 5 步的试算一致。
7. **出报告、填反馈**：
   - 运行 `match report`；
   - 用浏览器打开 `report.html`，用 Excel 或 WPS 打开 `feedback.csv`，填好三列；
   - 告诉 Agent，由它汇总认可的情况。

顺不顺手（给规划者参考）：
- 第 1 步和第 4 步最费事：每个岗位都要重新导入，再由 Agent 重新补经历。真实岗位只有 5 个左右，还能接受。这是 M2-6b、M2-6c（规则版本 4、5）和 M2-6d（摘要的定义）带来的一次性代价，以后只改权重就不会再清空了。
- 第 6 步要逐个岗位运行 `match score --save`，岗位一多就麻烦。以后可以考虑加一个命令，把只因权重过期的记录一次重新评分。本 PR 不做。
- 顺序是个坑：先补了经历，再重新导入岗位或改薪资、城市，记录就又过期了，补过的经历要再补一遍。所以清单开头先讲顺序；match.md 第 7 条也写明了原因不同、做法不同。
- 在 Windows PowerShell 5.1 里，`--weights skills=30,direction=25,...` 不加引号也能整个传进去（本机试过），不需要额外提示。
- V20（Codex B 用示例数据把这份清单完整演练了一遍，2026-10-30）提了三处，都已改：
  - 第 2 步原来先 `profile validate` 再 `match list`，但旧档案缺新字段时 `match list` 也报档案无效。现在第 2 步只诊断档案，`match list` 挪到第 3 步校验通过以后；
  - 手工读写的文件也要用同一个数据目录。现在清单开头先定数据目录，并列出各个文件的完整路径；
  - "旧记录里的经历已经清空"不准确：重新评分生成的新草稿里判断是空的，保存成功后才替换旧记录。措辞已改。
