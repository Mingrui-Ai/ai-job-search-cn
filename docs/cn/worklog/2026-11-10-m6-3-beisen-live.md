# 2026-11-10 · M6-3 北森适配器第一次真实运行读不到岗位：诊断和修复

接 [M6-3 北森适配器](2026-11-10-m6-3-beisen.md)（PR #149）。本次修复是 PR #150。真实页面、公司名和岗位原文只存在本机（仓库外），这里只写结构。

## 现象

第一次在本机白名单的 5 家真实门户上运行（新版 4 家、旧版 1 家），全部 0 条：两家新版门户第 1 次加载就报 `page_changed`（“搜索结果页上找不到岗位卡片”），其余三家（新版 2 家、旧版 1 家）每组搜索都是 `no_results`。其中一家新版门户的实习频道，调研时明明有符合关键词的岗位。

## 诊断

1. 离线：用 11-09 调研时存的真实页面对照规则。新版列表页的卡片选择器（`STListItem`）在真实页面上能匹配；新版详情页的 DOM 规则能读出标题、标签、日期和两段正文；旧版列表页的表格行和 `/zpdetail/<数字>` 链接能读出来。调研只记了列表请求的键，没有记响应体，新版列表响应的格式离线无法确认。
2. 少量真实访问看结构：只限白名单 5 家，每家不超过 2 次列表加载（含一次滚动）和 1 次详情，间隔 4–9 秒，全程没有遇到 403、429、验证码或跳登录。只导航、滚动和读渲染后的页面，被动记下页面自己发出的列表、详情请求的请求体和响应体；不登录，不读 Cookie，不自己发请求。结果存在仓库外的本机目录。

## 原因

- **新版列表响应的岗位 ID 取错了字段（主因）。** 真实响应是 `{"Code":200,"Message":…,"Count":<总数>,"Data":[…],"Total":0,…}`。每条岗位的 `Id` 才是详情页地址里的 `jobAdId`（UUID），`JobAdId` 是门户内部的整数编号。适配器按 `JobAdId`、`Id` 的顺序取第一个存在的键，拿到整数，于是每条都算“认不出”：没有卡片，又不是空结果，就报 `page_changed`。选择器没有错，搜索参数也生效了：页面发出的列表请求里 `LocId` 是 `["4401"]`，`KeyWords` 是地址里的关键词，结果数相应变少。
- **新版总数也取错了字段（潜在问题）。** 总数在 `Count`，`Total` 恒为 0。适配器读 `Total` 得 0，认为第一页之后没有更多；修好上一条后也只会读第一页（每页 20 条）。真实样本：一家门户广州校招共 32 条，第一次加载 20 条，滚动后页面自己发出第二个请求（`PageIndex` 从 0 起），带来其余 12 条。页面在第一页底部就显示“没有更多了~”，不能以它为准。
- **三家的 `no_results` 是真的没有结果。** 旧规则下新版报 `no_results` 的前提是响应里 `Data` 为空列表，所以这几组搜索在门户自己的搜索里确实没有结果。抽查的新版空结果页：响应 `Count` 为 0、`Data` 为空，页面显示“暂时没有符合条件的职位~”空态框和“共 0 个”。旧版空结果页：“共0条记录”和“没有搜索到相关应聘职位。”。
- **但空结果判断太宽。** 旧版只要页面上有“共 N 条”就算空，不看 N 是几；新版只看响应，不看页面的空态。认不出卡片时可能被当成没有结果。
- **旧版详情页（之前没有样本）读不出来。** 标题在 `.xiangqingtitle` 里，后面跟着“(未申请)”状态；字段的标签和值分在两个元素里（`li.ntitle` 和 `li.nvalue`，正文区是相邻的两个 `p`）。原规则按猜的选择器找标题、按同一行“标签：值”读字段，都读不到，第一次打开详情就会停。页面侧栏的搜索表单也有“工作地点：”，读字段时必须限定在岗位本身的区域。
- **时序。** 空态框可能在列表响应到达之前就出现（一次抽查里早 0.2 秒，随后出现加载遮罩，响应到达后再出现），“共 0 个”也是。所以空态框不能当作列表已就绪的信号：空结果仍要等就绪超时，再同时看响应和页面。

## 修复

- 新版列表：岗位 ID 只取 `Id`（UUID），岗位名取 `JobAdName`，薪资取 `Salary`（`null` 不写），地点取 `LocNames`；总数取 `Count`。响应必须是 `Data` 列表加 `Count` 整数，否则按页面结构变了停下（原来猜的 `Data` 里唯一列表、`TotalCount` 等写法都删掉）。有了 `Count`，第一页之后会滚动加载，直到读够总数；“没有更多了~”不再参与判断。
- 新版空结果：响应 `Count` 为 0、没有岗位（也没有认不出的岗位），且页面显示空态框、没有卡片，才算没有结果。就绪信号仍只等卡片（以及验证码、登录），不等空态框。
- 旧版空结果：没有岗位链接，且写着“共0条”或显示无结果框；写着“共 N 条”（N 大于 0）时一律不算空。
- 旧版详情：只在岗位本身的区域里读；标题去掉“(未申请)”；“标签：”元素取紧跟的值元素（也兼容同一元素里的“标签：值”）；正文按标题收集到下一个标题或标签为止，不越出岗位区域。就绪选择器改成岗位标题和正文区。
- 护栏和停止条件都没有动：403/429、验证码、跳登录、接口报错、详情页对不上、连续两次加载没有新岗位、每次 5 次列表和 30 个详情的上限、4–9 秒间隔，以及审核修的两处（延迟送达的接口错误在下一次导航或滚动之前停下、主文档非 2xx 不解析），对应测试原样通过。`browser.py`、`collect.py`、`tools/security_guards.py` 没有改。

## 测试

`tests/test_cn_beisen.py` 的样例全部换成照真实结构手写的虚构内容（公司、岗位、正文都是虚构的，只保留 DOM 和 JSON 的结构）：列表响应的键和类型、无链接的卡片、页面底部过早的“没有更多了~”、新版详情、旧版列表（含翻页条）、旧版详情（含侧栏搜索表单的“工作地点：”、标题后的申请状态、分开的标签和值）、两版真实的空结果页。新增：

- 新版只有 `JobAdId` 数字、`Id` 不是 UUID 时报 `page_changed`，不是 `no_results`；`Id` 读成岗位 ID，`Count` 决定还有没有更多（`Total` 为 0 不影响）。
- 新版空结果：响应和页面都说没有才算；页面有卡片、没有空态框、`Count` 大于 0、列表响应没到、岗位认不出，都报 `page_changed`。
- 旧版空结果：“共0条”、无结果框各自都算；链接认不出、“共 N 条”下没有行，报 `page_changed`。
- 写着有岗位却一条也读不出：两版都在第一次加载就停（原来要再加载一次）。
- 空态框和“共 0 个”不在就绪选择器里。
- 旧版详情的正文行、薪资、工作性质、发布时间和标题逐行核对；没写薪资的不写，“面议”照写。

## 真实验收

在主工作树的数据目录上，对一家新版门户跑了一次：只读实习频道、广州，不带关键词（`--all`），默认上限，单独一个批次（批次名和输出存在仓库外的本机任务目录）。结果：完成（`end_of_list`），1 次列表加载、3 个详情页，新存 3 个岗位，跳过 0，没有警告，退出码 0，详情之间间隔约 8 秒。调研时看到、上一次没读到的那个岗位也在其中。

每个文件的字段：`format`、`site: ats`、`site_job_id`（`beisen.<租户>.<UUID>`）、`url`（这个 UUID 的详情页）、`fetched_at`、`text`、`extra`（租户、频道、职位编号、采集器、空关键词、城市、列表地点、序号）。正文依次是岗位名（编号已去掉）、招聘频道、工作地点、工作性质、发布时间、公司名称、职位编号和“工作职责”“任职资格”两段；页面没写薪资，所以没写，导入后为 `null`。三条都能被收件格式读入，`jd parse` 读出标题、公司、城市广州、实习、发布日期，Schema 校验无错误；没有乱码。没有运行 `jd screen`，其他几家等合并后再采。

## 遗留

- 新版门户的岗位下线后，详情页和详情接口是什么样子没有样本：如果详情接口报错，会按“接口报错”停下整家租户。
- 新版的空结果每组要多等约 15 秒（就绪等待超时）才判断；档案关键词多、空结果多时一次运行会慢一些。
- 列表请求里的城市（`LocId`）这次核对过是地址里的城市代码，但适配器只核对关键词，城市不对时只在多数岗位不在该城市时给警告。

## 验证
