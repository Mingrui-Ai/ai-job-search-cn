# 2026-10-28 · M2-4b 规则评分与匹配记录

**完成**

- `jobsearch_cn/score.py`：按 [match.md 的设计稿](../match.md#可解释评分m2-4-设计稿)算出匹配记录的规则部分。
  - 硬性过滤的结论；
  - 技能：按掌握程度记分，`same_as` 里的同义写法算同一个技能；
  - 方向：JD 技能数量最多的词表分组，和档案的 `target.directions` 比较；
  - 薪资：同单位时，JD 上限和档案的最低期望比较；
  - 以上三个维度为 0–100，或者为 null；
  - 经历留给 Agent，附上提示（档案里用到 JD 技能的经历）；
  - 权重、四舍五入取整的总分、等级（被过滤掉的记为 `ineligible`），以及附 JD 原文的缺口。
- 岗位和档案的摘要：岗位的摘要不含 `status`，档案的摘要不含 `contact`。两边都没变时，重新评分保留 Agent 补的经历和方向；有一边变了就清空。
- `score.validate()`：
  - 先核对摘要；
  - 再重算规则部分和总分，和记录不一致就报错；
  - Agent 补的维度要有理由，依据要引用 JD 原文和档案里存在的经历 id。
- `store.MatchStore`：每个岗位一个 `<数据目录>/matches/<岗位id>.json`，和岗位库共用原子写入。
- 命令 `match score [--save]`、`validate`、`save`、`show`、`list`；`list` 按等级、总分排序，标出过期的记录。
- `tests/test_cn_score.py`：
  - 各维度，包括每种为 null 的情形；
  - 总分和等级（含 62.5 记 63）、缺口；
  - 重复运行结果一致、摘要和过期、重新评分保留 Agent 补的内容；
  - `validate` 拒绝四种篡改，以及其他不允许的改动；
  - 改权重前后 `match list` 的两种排序；
  - 10 × 2 期望表，附人工核对说明。
- 文档：`match.md`（设计稿状态、实现补充、命令的输出和退出码）、路线图。

**决策**

- 期望表用原有 5 份样例和 V2 的 5 份，和 V5 是同一批 JD；H9 新加的 3 份样例不在表里。
- JD 里的同义写法只算一次：例如 JD 同时写了 K8s 和 Kubernetes，档案只有其中一个时，不会被算作缺一项。
- 方向数量并列时都算岗位方向：一份 JD 数据、技术各两项时，求职方向是其中任何一个都记 100。
- `match validate` 要求摘要和当前一致：岗位或档案改过以后，规则部分本来就会变，无法判断是谁改的，只能重新评分。
- 算分全程用分数，避免浮点误差让同一输入得到不同的结果。
- `match score --save` 的输出和不加时一样，都是匹配记录本身，方便 Agent 直接拿去补充、校验、保存。

**验证**

- 期望表 20 组都和人工核对的结果一致，记录都能通过 `validate`。
- 用户的真实档案在本机试评分，只看汇总、不保存，没有写入 `data/matches/`：
  - 5 份岗位过滤结论都是 `needs_check`，共 9 项未知；
  - 等级都是 moderate，总分 52–53；
  - 技能 11–13 分，方向都是 100，薪资都为 null（档案没写最低期望），经历等 Agent 补；
  - 缺口共有 31 项技能、9 项过滤；
  - 记录都能通过 `validate`，记录里没有联系方式。
- 变异测试共 21 项，每项都有测试失败。
  - 技能与方向：同义词算两次、没写程度但用过的记 0.5、`general` 也计入方向、并列只取一个组、没有 50 分这一档；
  - 薪资与总分：薪资要求高于而不是达到、单位不同照样比较、四舍五入改成银行家舍入、被过滤掉的不记 `ineligible`、不用档案的权重；
  - 校验：不查总分、不查 JD 原文、不查经历 id、不查规则维度、过期的记录也放行；
  - 摘要与重新评分：岗位改了也保留 Agent 补的内容、摘要算进 `status`、摘要算进 `contact`；
  - 命令：`list` 只按总分排序、`list` 不标过期、`score --save` 不保存。
- 本地全量测试共 1104 项，1094 项通过、10 项按预期跳过；`security_guards`、`lint_skills` 通过（conda `ai-job-search-cn`，Python 3.12.15）。
