### 三档城市与薪资对照

所有 JD 均源于公开的 `tests/fixtures/cn/jd/boss_intern.txt`。主组三份只改工作地点行：深圳原文、杭州·西湖区、北京·海淀区；公司及职责要求保持原文。另加两份薪资控制样例：深圳改为 100–120 元/天、杭州改为 300–350 元/天。全部留在本地数据目录，不提交。

五份依次执行 `jd parse --save` → `jd show` → `match score --draft`。解析结果分别只有预期的工作城市，没有把示例公司名中的深圳混进杭州/北京城市列表。只有草稿时，`match list` 为 0 条。

经历统一由本次 Codex 判断为 90：`exp-1` 的 Go 订单查询接口重构与 JD 的 Go 后端职责直接相关，`proj-1` 的 MySQL 项目可以迁移；未声称做过 Redis/Kubernetes。引用 JD 原文“参与公司核心业务系统的后端开发，使用 Go 语言编写高并发服务”“参与 MySQL、Redis 等存储方案的设计与优化”和真实 fixture 经历 id。其他维度、hints、权重及缺口不改。

每份均实际执行：补经历 → `match validate` 返回唯一的 `total: ... they give {...}` 错误 → 原样复制提示中的 JSON 对象 → 再校验通过 → `match save` → `match show`。读回与草稿完整相等；五份中四个规则维度也分别与最初草稿一致。第一次本地驱动把该对象当 Python 字面量读取失败，改为 JSON 解码后继续；这是验证辅助脚本的问题，不是产品失败，没有改 CLI 或评分记录规则。

五份的技能 / 方向 / 经历均为 52 / 100 / 90，权重均为 30 / 25 / 25 / 10 / 10；补完后 `complete=true, missing=[]`。北京的地点分 0 不代表硬条件冲突：档案接受远程、JD 未写能否远程，所以是待确认。杭州地点检查为 match，附“不是首选”的 note。

**第 6 步的中文解释（本次合成场景）**：

> 深圳原样例符合硬条件，83 分，很匹配；杭州是可以接受但非首选的城市，地点 60，完整评分 79，比其余条件相同的深圳少 4 分。杭州薪资上限 250 元/天，达到最低期望 150 元/天，薪资分为 100；相较“首选深圳但薪资上限只有 120”的 73 分，它高 6 分：薪资达标带来的 10 分抵消了地点少的 4 分。它仍比同样薪资达标的深圳低 4 分，不能说薪资把一切地点损失都补回。
>
> 北京不在两档城市里，且不考虑异地，地点 0；薪资达标后完整总分 73，较匹配。不过 JD 没写能否远程，硬条件为待确认，先查原文或问 HR，不能据 73 分当成已确认能投。杭州薪资提高到 300–350 后仍为 79，因为当前薪资规则只判断“上限达到最低期望”，不按超出幅度继续奖励，也不代表一定能拿到上限。
>
> 各场景技能 52：五项要求满足三项，Golang 或 Java 按任选其一计，缺 Redis、Kubernetes；方向为技术，100；经历 90 来自上述两段原文和 exp-1/proj-1。低薪深圳另有薪资缺口；北京另有地点待确认。三个维度的这些判断不因城市替换而变。保存后的完整评分不能继续套用文档中“经历未补、分母 75”的 81/75/67 算例。

另以单独档案副本做只读补充检查（不覆盖正式匹配）：北京 + `relocate=true` 得地点 30、硬条件 match；`relocate=null` 得地点 0、硬条件 unknown 且校验警告；`remote_ok=false, relocate=false` 得地点 0、硬条件 conflict/ineligible；两档城市都空时地点 null。它们因档案变化，经历恢复为待补，没有混入上表。
