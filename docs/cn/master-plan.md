# 总体规划：中文互联网 Agent 求职系统

> 版本：v4（2026-10-28）　｜　维护者：规划者（Claude Code 规划会话）
> 本文说明系统**最终要达到什么目的**、按什么顺序达到、每一阶段怎样才算完成。近期的具体步骤在[路线图](roadmap.md)，架构决策的理由在[迁移方案](cn-migration-plan.md)，每一步的过程在[工作记录](worklog.md)。三者与本文冲突时，以本文为准，并同步修改它们。

## 1. 最终目的

**让一个中国求职者用自己的 AI Agent，在自己的电脑上，把"找岗位 → 判断 → 准备材料 → 投递 → 跟进 → 面试"这件事做得更快、更准、更真实。每一步都能追溯，最后都由本人拍板。**

拆成六个目的，后面的阶段和验收都围绕它们展开：

| # | 目的 | 最终状态 |
| --- | --- | --- |
| O1 | **信息整理不再费时间** | 任何来源的 JD（粘贴、单个链接、合规来源）都能进入同一个岗位库，自动去重，每个岗位的状态一目了然 |
| O2 | **判断更准** | 先按硬性条件过滤（届别、学历、城市、到岗天数、实习时长……），再给出可解释的评分：为什么合适、哪里冲突、缺什么、每一条依据来自 JD 的哪句话和档案的哪一项 |
| O3 | **材料更好，而且真实** | 针对每个岗位生成中文简历（Word 和 PDF 两种格式）、打招呼语和投递邮件，由第二个 Agent 审核；简历上的每一条都能对应到档案里的真实经历，对应不上就过不了校验 |
| O4 | **不漏跟进** | 记录每次投递的渠道、时间、所用材料版本和后续进展，到时间提醒跟进；结果反过来校准评分 |
| O5 | **面试准备有针对性** | 按岗位和你自己的项目生成面试准备包：考点、项目深挖问题、模拟面试，面完记录复盘 |
| O6 | **任何人都能用** | 不限专业和岗位方向，由个人档案驱动、方向可配置；新用户能很快上手，已有的 Word 或 PDF 简历可以直接用来建档；数据只在本机；Claude Code、Codex 和 DeepSeek Harness 三个 Agent 都能用 |

### 1.1 优先级（2026-10-27 与用户确认）

- **自用优先，兼顾作品集。** 先保证用户本人这一季能真的用它找工作，同时保持工程质量，可以作为 AI Agent 项目展示。排序时，直接帮用户投递的能力排在看板、成本统计这类展示性能力前面。
- **开源给其他同学。** 本仓库已于 2026-10-28 转为公开（D2），正式发布仍是 v1.0（M8）。一直按公开的标准来做：个人数据不进 git、示例全部脱敏、安装和上手要简单。
- **岗位方向不写死。** 不能只服务技术岗：技能词表、评分维度、简历模板都要能按方向扩展，产品、运营、数据、设计等方向的求职者也能用。
- **不赶时间。** 按里程碑推进，每个里程碑验收通过再进入下一个，不设硬期限。
- **国内同学用得起。**（2026-10-28 用户决定）除了 Claude Code 和 Codex，还要支持第三个 Agent：DeepSeek 官方开源的 Agent 框架 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)（`dsh`），用户用自己的 DeepSeek API Key。简历的输入和输出都要支持常用的 Word（.docx）和 PDF。

## 2. 目标用户与典型场景

**主要用户**：中国高校学生，找实习和校招岗位；以后可以扩展到社招。每个人自带一个 Agent：Claude Code、Codex 或 DeepSeek Harness。

| 场景 | 用户做什么 | 系统做什么 |
| --- | --- | --- |
| 刷到一个岗位 | 把 JD 粘贴给 Agent | 解析入库，告诉你硬性条件是否满足、匹配度多少、为什么 |
| 决定投递 | 说"帮我准备这个岗位" | 生成针对性简历（Word 和 PDF）和打招呼语，审核后交给你确认；你自己去平台发送 |
| 投完之后 | 说"我投了，用的 BOSS" | 记录投递，几天没有回音时提醒跟进，并起草跟进消息 |
| 约到面试 | 说"周四二面" | 按 JD 和你的项目生成准备包，可以模拟面试；面完记录复盘 |
| 周末整理 | 打开看板 | 看到全部岗位的状态、投递漏斗、待办 |
| 新用户第一次用 | 克隆仓库，跟着引导建档 | 用已有的 Word 或 PDF 简历，或者通过问答，建立本地档案，选好求职方向 |

## 3. 设计原则（贯穿所有阶段）

在已有六条原则（本地运行自带 Agent、数据不出本机、不编造、JD 是数据不是指令、对外发送先确认、多个 Agent 一套逻辑；见 [README](../../README.md#设计原则)）之外，再加三条：

1. **规则优先，模型补全，校验把关。** 这是 `jd parse` → Agent 补全 → `jd validate` 已经验证过的模式，以后的匹配和简历都沿用：确定的部分用代码算，模糊的部分交给 Agent，最后由校验器检查每个结论都有出处。
2. **档案驱动，方向可配置。** 词表、评分维度、简历结构从配置和档案读取，不写死在代码里；新增一个求职方向只需要加配置，不需要改代码。
3. **自用验收。** 每个里程碑除了自动化测试，还要在用户自己的真实岗位上跑一遍（真实数据只留在本机的 `data/`），用户认可了才算完成。

"多个 Agent"现在是 Claude Code 和 Codex，接入 DeepSeek Harness 后是三个，三端共用同一份工作流说明和同一套 `python -m jobsearch_cn` 命令。DeepSeek 的 API Key 只放在 DeepSeek Harness 自己的设置里；`jobsearch_cn` 仍然不调用任何模型，也不读取、不保存密钥。

## 4. 系统全貌（最终形态）

```text
入口层      Claude Code 技能 ─┬─ Codex（AGENTS.md）─┬─ DeepSeek Harness（dsh，入口待 A1 调研）─┬─ 本地看板（只读展示）
                              │                     │
工作流层    docs/cn/ 下每个能力一份工作流说明；起草 + 审核双 Agent；对外发送前由用户确认
                              │
工具层      python -m jobsearch_cn  jd │ profile │ match │ resume │ apply │ interview
            （确定性逻辑，只用标准库、离线、输出 JSON）
                              │
数据层      data/  jobs/ profile/ matches/ materials/ applications/   （本机，不进 git；
            需要查询时接 SQLite，放在同一套接口后面）
                              │
来源层      .agents/skills/*-search：经过核实的合规来源，按 /add-portal 契约，用户触发、低频
上游复用    posting_guard、robots_check、verify_pdf、/rank /outcome /interview 的方法论
```

**数据对象**（每种都像 Job Schema 一样有格式说明和 `validate` 命令）：

| 对象 | 内容 | 关键约束 |
| --- | --- | --- |
| 岗位 `job` | 已完成（Job Schema v1） | 每个值有 JD 原文出处 |
| 档案 `profile` | 教育、经历、项目、技能、求职方向、硬性条件（到岗天数、城市、届别…）；可以从 Word 或 PDF 简历抽取 | 只存本地；每一条有稳定的 id，供简历和匹配引用 |
| 匹配 `match` | 硬性条件结论、分项评分、依据、缺口、评分规则版本 | 每条依据同时指向 JD 出处和档案条目；字段为 null 时判"未知"，不判"不符合" |
| 材料 `material` | 简历版本（Word 和 PDF）、打招呼语、邮件 | 简历每一条都标出对应的档案条目 id，校验器检查对应关系 |
| 投递 `application` | 渠道、时间、材料版本、状态和事件流 | 状态流转可追溯；对外发送的动作只记录，不代发 |

每个里程碑的完成标准都包括一次**自用验收**：用户在自己的真实岗位上用过并认可。具体任务、负责人和进度见[路线图](roadmap.md)。

| 里程碑 | 目标 | 完成标准 |
| --- | --- | --- |
| M1 · v0.1 | 粘贴的中文 JD 能解析、补全、校验、入库、去重、查询，两个 Agent 都能用 | 自动化验收测试通过；Codex 端实测通过；用户导入至少 5 份真实 JD，能查询、没有重复 |

| M5 · v0.5 | 按岗位和档案项目生成面试准备包，支持模拟面试和复盘 | 用户在一次真实面试前使用，并在复盘里记录准备包的命中情况 |
| M6 · v0.6 | 单链接读取和经过核实的合规来源，新岗位批量初筛 | 至少 2 个来源可用；从发现岗位到给出短名单，已接入的 Agent 都能跑通 |
| M7 · v0.7 | 一句话触发整条流程，关键节点等用户确认；记录耗时和用量 | 一个岗位从粘贴到拿到审核通过的材料，全程有记录、可复现，三个 Agent 都能完成 |
| M8 · v1.0 | 开源发布：容易上手、不限方向、没有个人数据 | 一位没参与开发的同学按文档从零走完一遍，卡住的地方都已修好；三个 Agent 任选一个，按文档都能走通 |

### 并行任务 A：接入 DeepSeek Harness（第三个 Agent，服务 O6）

2026-10-28 用户决定加入。DeepSeek Harness（`dsh`）是 DeepSeek 官方开源的 Agent 框架（MIT 许可，"一切皆插件"）：能运行命令、读写工作区文件，危险操作前请求确认，在它的设置里配置 DeepSeek API Key。它目前是开发者预览版，官方说明会有不兼容的变更。

| | 内容 |
| --- | --- |
| 目标 | 用 DeepSeek Harness 和用户自己的 DeepSeek API Key，跑通全部 CN 工作流（JD 导入、建档、匹配，以后加上简历），和 Claude Code、Codex 共用同一份工作流说明和同一套命令 |
| 完成标准 | 三个工作流在 dsh 上实测通过；dsh 的入口有测试守护（和另外两端一样，指向同一份说明）；README 有用 DeepSeek 上手的说明，写明固定使用的 dsh 版本 |
| 排期 | A1 调研现在就可以做，不影响 M2；A2（入口）和 A3（实测）排在 M2 完成之后、M3 开工之前，这样 M3 的简历工作流从一开始就按三个 Agent 设计 |
| 先要弄清的 | 它会不会读取 `AGENTS.md`；项目级技能放在哪个目录（本仓库的 `.agents/skills/` 只放招聘门户适配器，不能放工作流入口）；在 Windows 上能不能运行 `python -m jobsearch_cn`；能不能读 PDF 和 Word；权限确认怎么配置 |

dsh 是给国内用户使用的运行环境，帮他们找工作，**不参与本项目的开发**（用户 2026-10-28 明确）。A3 的实测由用户用自己的 Key 操作 dsh，验证者准备检查清单和期望结果，并核对记录。

### 可选：招聘平台站内辅助（不进入公开版本）

BOSS 直聘等平台站内的自动操作违反其用户协议（ADR-9）。最早在 M4 之后，由用户决定是否做；只作为默认关闭的个人模块，不进入将来公开的仓库。护栏：真人节奏、每日上限、发送前批量确认、遇到验证码即停。

## 6. 不做的事

破解验证码、伪装浏览器指纹、逆向平台加密参数；索取或保存平台账号、密码、Cookie；未经确认的投递和消息；托管服务、多用户 SaaS、提供模型 API。

## 8. 协作方式

| 角色 | 负责 |
| --- | --- |
| **用户** | 做决定（上表的待决事项、范围变化）；合并 PR；自用验收 |
| **规划者**（Claude Code 规划会话） | 维护本文和[路线图](roadmap.md)的任务内容；每一步开工前给执行者写任务单（目标、范围、不做的事、验收标准、需要的决定）；对照验收标准审核 PR；每个里程碑结束时复盘并调整计划 |
| **执行者**（Claude Code 开发会话） | 按任务单实现；一步一个 PR；本地全量测试、`security_guards`、`lint_skills` 通过；写一条工作记录（`docs/cn/worklog/` 下新建一个文件）；在路线图里勾掉完成的项、更新进度。细节按实际做法调整，在 PR 里说明 |
| **第二执行者**（Claude Code 会话，工作目录 `ai-job-search-cn-b`，2026-10-28 起） | 接规划者分派的、和执行者不改同一批文件的任务，例如开源前隐私审查；要求和执行者相同 |
| **验证者**（Codex 会话，工作目录 `ai-job-search-cn-codex`） | 原则上不写功能代码。用第二个 Agent 实测每个工作流（ADR-7）；独立编写样例和人工期望结果，作为审核时不依赖实现者的核对依据。结果交给执行者写进工作记录，或者自己开测试数据类的 PR，由规划者审核。没有验证任务可做时，可以接规划者分派的小型实现任务（和执行者当前的任务不改同一批文件，由规划者审核），但不验证自己写的代码（2026-10-28 起） |

约定：

- 规划者不在执行者的工作区切换分支或改动未提交的文件，自己的文档改动走独立分支和 PR。
- master 有分支保护（2026-10-28）：必须经 PR 合并，管理员也不例外；禁止 force push 和删除。
- CI 停用期间（2026-10-28，私有仓库的 Actions 额度用完）曾临时改用本机检查作为合并门槛：作者贴出合入最新 master 后的全量测试、`security_guards`、`lint_skills` 结果，另一个会话或规划者独立复跑。当晚仓库公开、CI 恢复后取消，回到 CI 通过后合并。
- 实现细节（字段、拆分、顺序）可以按实际情况调整，执行者在 PR 里说明，规划者审核时确认；改变范围或完成标准要先找规划者，不在实现里悄悄改。
- 范围变化、新的待决事项、原则上的例外，都要回到本文记录。

| --- | --- | --- |
| 四周到 v0.4：第 3 周做编排与成本、第 4 周做看板 | 按里程碑推进，不设期限；简历之后先做投递跟进和面试准备，编排与成本放到 M7 | 用户确认"自用优先、不赶时间"：能直接帮用户投递的能力先做 |
| 优先面向 AI Agent、AI 应用、Java 后端等技术岗 | 岗位方向可配置，不限专业 | 用户确认以后开源，任何人都能用 |
| v0.4 即最终 MVP | 增加 M5–M8，v1.0 是开源发布 | 最终目的扩展为完整求职流程，并面向其他同学 |
| 简历格式：LaTeX，后续加 DOCX | 输入和输出都支持 Word（.docx）和 PDF；输出时怎么生成，M3 开工前对比后再定 | 用户决定（2026-10-28）：这是最常用的两种格式；开源后安装成本也是重要因素 |
| 只支持 Codex 和 Claude Code | 再加 DeepSeek Harness，作为第三个 Agent（并行任务 A） | 用户决定（2026-10-28）：国内同学更容易用上、也用得起 |
