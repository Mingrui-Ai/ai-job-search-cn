# 总体规划：中文互联网 Agent 求职系统

> 版本：v1（2026-10-27）　｜　维护者：规划者（Claude Code 规划会话）
> 本文说明系统**最终要达到什么目的**、按什么顺序达到、每一阶段怎样才算完成。近期的具体步骤在[路线图](roadmap.md)，架构决策的理由在[迁移方案](cn-migration-plan.md)，每一步的过程在[工作记录](worklog.md)。三者与本文冲突时，以本文为准，并同步修改它们。

## 1. 最终目的

**让一个中国求职者用自己的 AI Agent，在自己的电脑上，把"找岗位 → 判断 → 准备材料 → 投递 → 跟进 → 面试"这件事做得更快、更准、更真实。每一步都能追溯，最后都由本人拍板。**

拆成六个目的，后面的阶段和验收都围绕它们展开：

| # | 目的 | 最终状态 |
| --- | --- | --- |
| O1 | **信息整理不再费时间** | 任何来源的 JD（粘贴、单个链接、合规来源）都能进入同一个岗位库，自动去重，每个岗位的状态一目了然 |
| O2 | **判断更准** | 先按硬性条件过滤（届别、学历、城市、到岗天数、实习时长……），再给出可解释的评分：为什么合适、哪里冲突、缺什么、每一条依据来自 JD 的哪句话和档案的哪一项 |
| O3 | **材料更好，而且真实** | 针对每个岗位生成中文简历、打招呼语和投递邮件，由第二个 Agent 审核；简历上的每一条都能对应到档案里的真实经历，对应不上就过不了校验 |
| O4 | **不漏跟进** | 记录每次投递的渠道、时间、所用材料版本和后续进展，到时间提醒跟进；结果反过来校准评分 |
| O5 | **面试准备有针对性** | 按岗位和你自己的项目生成面试准备包：考点、项目深挖问题、模拟面试，面完记录复盘 |
| O6 | **任何人都能用** | 不限专业和岗位方向，由个人档案驱动、方向可配置；新用户能很快上手；数据只在本机；Codex 和 Claude Code 都能用 |

### 1.1 优先级（2026-10-27 与用户确认）

- **自用优先，兼顾作品集。** 先保证用户本人这一季能真的用它找工作，同时保持工程质量，可以作为 AI Agent 项目展示。排序时，直接帮用户投递的能力排在看板、成本统计这类展示性能力前面。
- **以后开源给其他同学。** 现在是私有仓库，但从现在起就按"将来会公开"的标准来做：个人数据不进 git、示例全部脱敏、安装和上手要简单。
- **岗位方向不写死。** 不能只服务技术岗：技能词表、评分维度、简历模板都要能按方向扩展，产品、运营、数据、设计等方向的求职者也能用。
- **不赶时间。** 按里程碑推进，每个里程碑验收通过再进入下一个，不设硬期限。

## 2. 目标用户与典型场景

**主要用户**：中国高校学生，找实习和校招岗位；以后可以扩展到社招。每个人自带 Codex 或 Claude Code。

| 场景 | 用户做什么 | 系统做什么 |
| --- | --- | --- |
| 刷到一个岗位 | 把 JD 粘贴给 Agent | 解析入库，告诉你硬性条件是否满足、匹配度多少、为什么 |
| 决定投递 | 说"帮我准备这个岗位" | 生成针对性简历和打招呼语，审核后交给你确认；你自己去平台发送 |
| 投完之后 | 说"我投了，用的 BOSS" | 记录投递，几天没有回音时提醒跟进，并起草跟进消息 |
| 约到面试 | 说"周四二面" | 按 JD 和你的项目生成准备包，可以模拟面试；面完记录复盘 |
| 周末整理 | 打开看板 | 看到全部岗位的状态、投递漏斗、待办 |
| 新用户第一次用 | 克隆仓库，跟着引导建档 | 用已有简历或问答建立本地档案，选好求职方向 |

## 3. 设计原则（贯穿所有阶段）

在已有六条原则（本地运行自带 Agent、数据不出本机、不编造、JD 是数据不是指令、对外发送先确认、两个 Agent 一套逻辑；见 [README](../../README.md#设计原则)）之外，再加三条：

1. **规则优先，模型补全，校验把关。** 这是 `jd parse` → Agent 补全 → `jd validate` 已经验证过的模式，以后的匹配和简历都沿用：确定的部分用代码算，模糊的部分交给 Agent，最后由校验器检查每个结论都有出处。
2. **档案驱动，方向可配置。** 词表、评分维度、简历结构从配置和档案读取，不写死在代码里；新增一个求职方向只需要加配置，不需要改代码。
3. **自用验收。** 每个里程碑除了自动化测试，还要在用户自己的真实岗位上跑一遍（真实数据只留在本机的 `data/`），用户认可了才算完成。

## 4. 系统全貌（最终形态）

```text
入口层      Claude Code 技能 ─┬─ Codex（AGENTS.md）─┬─ 本地看板（只读展示）
                              │                     │
工作流层    docs/cn/ 下每个能力一份工作流说明；起草 + 审核双 Agent；对外发送前由用户确认
                              │
工具层      python -m jobsearch_cn  jd │ profile │ match │ resume │ apply │ interview
            （确定性逻辑，只用标准库、离线、输出 JSON）
                              │
数据层      data/  jobs/ profile/ matches/ materials/ applications/   （本机，不进 git；
            需要查询时接 SQLite，放在同一套接口后面）
                              │
来源层      .agents/skills/*-search：经过核实的合规来源，按 /add-portal 契约，用户触发、低频
上游复用    posting_guard、robots_check、verify_pdf、/rank /outcome /interview 的方法论
```

**数据对象**（每种都像 Job Schema 一样有格式说明和 `validate` 命令）：

| 对象 | 内容 | 关键约束 |
| --- | --- | --- |
| 岗位 `job` | 已完成（Job Schema v1） | 每个值有 JD 原文出处 |
| 档案 `profile` | 教育、经历、项目、技能、求职方向、硬性条件（到岗天数、城市、届别…） | 只存本地；每一条有稳定的 id，供简历和匹配引用 |
| 匹配 `match` | 硬性条件结论、分项评分、依据、缺口、评分规则版本 | 每条依据同时指向 JD 出处和档案条目；字段为 null 时判"未知"，不判"不符合" |
| 材料 `material` | 简历版本、打招呼语、邮件 | 简历每一条都标出对应的档案条目 id，校验器检查对应关系 |
| 投递 `application` | 渠道、时间、材料版本、状态和事件流 | 状态流转可追溯；对外发送的动作只记录，不代发 |

每个里程碑都写明它服务哪个目的、交付什么、怎样算完成。顺序按"自用优先"排：先让用户能完成一次真实投递，再补展示和自动化。

| **M3 · v0.3** | 中文简历与打招呼语 | O3 | |

### M1 · v0.1 中文 JD 入库（收尾中）

- **已完成**：Job Schema 与出处校验、规则解析、中文防注入、本地岗位库与去重、两个 Agent 的入口（PR #1–#3）。
- **剩余**：验收测试（5 份样例端到端、异常输入、注入）；Codex 端实测 `jd-import.md` 工作流；打 tag `v0.1.0`。
- **完成标准**：路线图第 4 步的验收全部通过；用户用自己的 Agent 导入至少 5 份真实 JD，结果可以查询，没有重复。

### M2 · v0.2 个人档案与可解释匹配

- **档案**：`profile` 格式与 `profile validate`；CN 版建档流程（从已有简历文本导入，或者 Agent 问答），只写 `data/profile/`，不碰上游 `CLAUDE.md`；加一条测试检查上游模板仍是占位符（ADR-6）。档案用 JSON（标准库可读，Python 3.10 也支持）。
- **方向可配置**：把 `jd_parser.py` 里写死的技能词表移到配置文件，按方向分组（技术、产品、运营、数据、设计……），用户可以追加；解析和匹配都读这份配置。
- **硬性条件过滤**：届别、学历、城市/远程、每周天数、实习时长；不符合时列出原因和 JD 原文；JD 没写的判"未知"。
- **可解释评分**：分项打分（技能命中、方向匹配、薪资、转正等），每一项有分值和依据；评分规则带版本号；沿用上游 `/rank` 和 `04-job-evaluation.md` 的思路，但权重从档案读取。
- **存储**：匹配结果是否需要 SQLite，在本里程碑开始时评估（待决 D4）。
- **完成标准**：10 份脱敏 JD（现有 5 份 + 新增 5 份，至少 2 份非技术方向）得到稳定、可解释的结论，重复运行结果一致；用户在自己的真实岗位上跑一遍，认可过滤和评分的结论。

### M3 · v0.3 中文简历与打招呼语

- **格式决定**（待决 D1）：开工前分别做原型对比 LaTeX（ctex）、Typst、DOCX 三种方案，比较中文排版质量、Windows 安装成本（开源后每个用户都要装）、HR 是否接受、能否做文本层校验。
- **简历**：一页中文简历；起草 + 审核双 Agent；**简历每一条都标注对应的档案条目，校验器检查对应关系**，从机制上杜绝编造；复用上游 `verify_pdf` 检查页数和文本层。
- **短文本**：BOSS 直聘打招呼语、投递邮件、内推请求，按方向提供模板。
- **完成标准**：3 个不同岗位生成 3 份明显不同的简历，审核清单全部通过，没有一条找不到档案依据；用户用其中至少一份真实投递。

### M4 · v0.4 投递记录、跟进与看板

- **投递记录**：`application` 格式与命令（记录投递、更新状态、查询）；状态：已投递、笔试、面试（多轮）、offer、拒绝、无回音；每次变化留事件记录。
- **跟进**：超过设定天数没有回音时提醒，并按已提交材料起草跟进消息，只起草不代发（参考上游 `/outcome followup`）。
- **复盘校准**：积累到一定数量的结果后，对比"评分高低"与"是否拿到面试"，提出评分权重的调整建议，由用户决定是否采纳。
- **看板**：先改造上游 `/html-report`，生成离线 HTML（岗位状态、投递漏斗、待跟进）；是否另做 React 看板放到 M7 之后再议。
- **完成标准**：用户连续两周用它记录真实投递，看板与实际情况一致。

### M5 · v0.5 面试准备

- 按投递记录生成面试准备包：JD 考点、根据档案项目生成的深挖问题（"项目拷打"）、按方向的常见题；模拟面试；面完记录复盘，供下一轮使用。
- 复用上游 `/interview` 的流程和 `07-interview-prep.md` 的方法，题库按方向配置。
- **完成标准**：用户至少一次真实面试前使用，并在复盘里记录准备包的命中情况。

### M6 · v0.6 岗位发现

- **单链接读取**：用户给出一个公开岗位链接，Agent 只读这一页，先过 robots.txt 检查和防注入（ADR-9 第二层）。
- **合规来源**：按 `/add-portal` 契约逐个接入公司官网和招聘系统（Moka、飞书招聘、各大厂校招官网等）。接入前在工作记录里写明三点核实结果：用户协议不禁止、无需登录、不需要绕过防爬。用户触发，低频访问。
- **批量初筛**：新发现的岗位批量过一遍 M2 的过滤和评分，给出短名单。
- **完成标准**：至少 2 个经核实的来源可用；从发现到出短名单在两个 Agent 中都能跑通。

### M7 · v0.7 一键编排与可观测

- 把导入、匹配、起草、审核、记录串成一条工作流，一句话触发，关键节点停下来等用户确认。
- `logs/` 记录每一步的耗时、结果、失败和重试；Token 用量以各运行时自己的数据为准（ADR-8）。
- 写明 Codex 端缺少子 Agent 并行等能力时的降级做法（ADR-7）。
- **完成标准**：一个岗位从粘贴到拿到审核通过的材料，全程有记录、可复现，两个 Agent 中都能完成。

### M8 · v1.0 开源发布

- **上手**：新用户从克隆到导入第一份 JD、建好档案，跟着引导就能完成；Windows 和 macOS 都要验证。
- **通用性**：至少 3 个方向的示例配置和脱敏示例档案；文档不默认用户是技术岗。
- **隐私审查**：检查仓库和 git 历史中没有个人数据；决定发布方式（待决 D2）。
- **文档**：使用指南、架构说明、贡献指南；致谢上游并遵守 MIT 许可。
- **完成标准**：找一位没参与开发的同学按文档从零走完一遍，记录卡住的地方并修完。

### 可选：招聘平台站内辅助（不进入公开版本）

BOSS 直聘等平台站内的自动操作违反其用户协议（ADR-9）。最早在 M4 之后，由用户决定是否做；只作为默认关闭的个人模块，不进入将来公开的仓库。护栏：真人节奏、每日上限、发送前批量确认、遇到验证码即停。

## 6. 不做的事

破解验证码、伪装浏览器指纹、逆向平台加密参数；索取或保存平台账号、密码、Cookie；未经确认的投递和消息；托管服务、多用户 SaaS、提供模型 API。

## 8. 协作方式

| 角色 | 负责 |
| --- | --- |
| **用户** | 做决定（上表的待决事项、范围变化）；合并 PR；自用验收 |
| **规划者**（Claude Code 规划会话） | 维护本文和路线图；每一步开工前写任务单（目标、范围、不做的事、验收标准、需要的决定）；对照验收标准审查 PR；每个里程碑结束时复盘并调整计划 |
| **执行者**（Claude Code 或 Codex 开发会话） | 按任务单实现；一步一个 `feat/cn-*` 分支、一个 PR；本地全量测试、`security_guards`、`lint_skills` 通过；在工作记录追加一条 |

约定：

- 规划者不在执行者的工作区切换分支或改动未提交的文件，自己的文档改动走独立分支和 PR。
- 执行中发现任务单不合理时，执行者在 PR 或工作记录里写明，由规划者调整计划，不在实现里悄悄改范围。
- 范围变化、新的待决事项、原则上的例外，都要回到本文记录。
