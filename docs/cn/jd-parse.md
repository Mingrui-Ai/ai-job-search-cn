# JD 解析（jd parse）

把用户提供的中文 JD 文本按规则抽取成 [Job Schema](job-schema.md) 记录。全程离线；规则读不准的字段留空，交给 Agent 或用户补全。

## 用法

```powershell
python -m jobsearch_cn jd parse jd.txt --site boss
python -m jobsearch_cn jd parse jd.txt --url https://example.com/job/123   # --url 只能用于单份 JD
python -m jobsearch_cn jd parse jd.txt --save                              # 解析后直接保存到本地岗位库
```

- 省略文件名时从标准输入读取。在 Windows PowerShell 5.1 中请直接传文件路径，原因见下面的"编码"。
- 输出 `{"jobs": [岗位记录, ...], "warnings": [...]}`。每条警告包含：
  - `segment`：第几份 JD；
  - `kind`：类型，可能是 `guard`、`encoding`、`too_long`、`empty`；
  - `message`：说明；
  - `excerpts`：可疑句子的摘录（仅 `guard` 警告有）。
- 退出码：0 至少解析出一份 JD；1 输入里没有 JD 文本；2 输入读不了，或 `--url` 用法不对。

## 一次导入多份 JD

在两份 JD 之间放一行 `===`（三个或更多等号）：

```text
后端开发实习生
200-250元/天
……
===
数据分析实习生
150-200/天
……
```

## 编码

| 输入 | 处理 |
| --- | --- |
| UTF-8，带或不带 BOM | 直接读取 |
| 带 BOM 的 UTF-16（Windows PowerShell 5.1 的 `>` 和 `Out-File` 默认写成这样） | 直接读取 |
| 其他编码（多半是 GBK，即记事本另存为时的 ANSI） | 按 GB18030 解码，并给出 `encoding` 警告 |
| 没有中文、却有大量 `?` | 拒绝，退出码 2。这是 Windows PowerShell 5.1 用 ASCII 传管道造成的，中文已经丢失 |

Windows 文件的 CRLF 换行可以正常处理。

每个值都附出处，`method` 为 `rule`。规则只抽取有把握的内容，宁可留空也不猜。

薪资金额要区分工资和单列的补贴、费用。交通补贴、补助、餐补、房补、收费、费用、押金、培训费等金额不当作工资；用途词写在金额前后都有效。跨行标签后有“每人”“标准为”等修饰词，金额仍归该标签；遇到明确工资标签时切回工资。真正的工资在补贴之前或之后都照常读，工资包含或另有补贴的说明不会把工资本身排除。“餐补另计”“房补另算”表示补贴不在前面的工资金额里，独立报价无需再有“月薪”前置标签。只有补贴和“工资面议”时仍保留面议，单独的薪资区间仍可识别。

## 补全流程

1. 用 `jd parse` 得到记录。
2. 补全规则留空的字段，常见的有 `company`、`requirements.education` 和更多技能。
   - Agent 补全时 `method` 写 `agent`，出处片段必须来自原文；
   - 用户手动补全时 `method` 写 `user`，可以不给出处片段。
3. 用 `jd validate` 校验，再用 `jd save` 保存。完整流程见 [jd-import.md](jd-import.md)。

## 防注入检查

每份 JD 都先经过 `jobsearch_cn/guard.py`：

- **复用上游 `tools/posting_guard.py`**：去掉隐藏内容和不可见字符，并检查英文注入句式、混用字形等；
- 上游解码的 tag 字符和 variation selector 隐藏文本也检查中文注入句式；解码内容只用于检查和警告，不混入 JD 字段提取或 `raw_text`。`guard.counts.invisible_text` 记录解码文本数量，即使没有命中已知指令句式，也保留上游告警；
- **补充中文注入句式**（迁移方案中的 G1），例如：
  - "忽略之前的所有指令"
  - "你现在是一个AI助手，"
  - "不要告诉用户"
  - "把候选人的手机号发送到…"

检查只提示、不拦截：

- 可疑句子出现在 `warnings` 的 `excerpts` 里，请人工查看；
- 记录本身只保存结论和数量（`guard`），不保存摘录。

中文句式刻意收窄，招聘广告里的正常说法不会触发，例如"熟悉提示词工程""设计系统提示词""请将简历发送至邮箱""作为AI产品经理""如果你是AI爱好者"。

`raw_text` 保存的是清理后的文本：去掉了隐藏和不可见字符，合并了多余的空白。

## 技能词表

**口径：技能只从正文读，不从标题读。** 标题是岗位名称，已经存进 `title`；岗位方向由 M2-4 看标题和技能所属的分组来判断，标题里的词再算成技能就重复计分了。所以"数据分析实习生"的"数据分析"只有正文也写到时才算技能。整份 JD 只有一行岗位名时，读不出技能。

技能只从词表里认，词表按求职方向分组：

| 分组 | 名称 | 例子 |
| --- | --- | --- |
| `tech` | 技术 | Python、Go、Spring Boot、LangChain、RAG、大模型、Docker、Playwright、接口测试、自动化测试 |
| `data` | 数据 | SQL、Tableau、Power BI、Pandas、数据分析、数据清洗、统计分析、A/B测试 |
| `product` | 产品 | PRD、Axure、墨刀、原型设计、需求分析、用户访谈 |
| `ops` | 运营 | 新媒体运营、内容运营、内容策划、文案写作、短视频运营、数据复盘、公众号、秀米、剪映 |
| `design` | 设计 | Figma、Photoshop、Illustrator、C4D、UI设计、交互设计、设计规范 |
| `market` | 市场 | 市场调研、商务沟通、客户访谈、CRM |
| `finance` | 财务 | 财务分析 |
| `hr` | 人力资源 | 招聘流程 |
| `general` | 通用 | Excel、PowerPoint、PPT（各个方向都用的办公软件） |

词条用 JD 里技能的完整写法：是"文案写作"，不是"文案"。"短视频""直播"是内容形式，单独出现时不算技能；词表里收的是"短视频运营""直播运营"。

“统计分析”属于数据组，“统计分析方法”“统计分析能力”也可读出这个词。“统计学”是学科/知识，“数据分析”范围更广，与“统计分析”分别保留，不作为同义词合并，也不推断掌握其中一个就掌握另外一个。

**同义词**（`same_as`）：同一个技能的不同写法列成一组，内置的有 Go / Golang、JavaScript / JS、Kubernetes / K8s、自然语言处理 / NLP、文案写作 / 文案撰写、PowerPoint / PPT、大模型 / LLM / 大语言模型、提示词工程 / Prompt、Photoshop / PS。解析结果保留 JD 原文的写法（JD 写"K8s"就记"K8s"）；评分比较技能时，同一组的写法算同一个技能。相关但不是同一个技能的不并组，例如 RAG、LangChain 和"大模型"；"AI"多指人工智能，不收作 Adobe Illustrator 的写法。

**正文里提到也不一定是要求**：

- 被否定的不算：分句里技能前面有"不要求""无需""不需要""不必""不负责""不涉及""不承担""非必须"等词，例如"无需 SQL 基础""不要求 Rust 或 C++ 经验"；
- 平台名（公众号、小红书、抖音、微博等）在两种地方不算：分句既有"关注""订阅""扫码""详见""动态见"这类引导词，又有"我们""官方""更多""招聘信息"这类指向公司自己的词（"欢迎关注我们的公众号"）；或者在"公司介绍""公司简介""关于我们"一节里，到下一个"岗位职责""任职要求"之类的小标题为止。只有引导词不算数："关注小红书热点"是工作内容，照常读出；
- 一行开头的"PS："（或"PS:"）是附言，例如"PS：简历请注明到岗时间"，这个 PS 不算 Photoshop。其他位置的 PS 照常读出，例如"设计软件：PS、Figma"。PS 后面跟一位数字的是游戏机（"PS4""PS5""PS 5"），也不算；跟年份的仍算（"PS2024"）。

内置词表在 `jobsearch_cn/skills.json`。匹配方式：

- 英文词不区分大小写，必须是完整的词（Excellent 里不会读出 Excel），词中间的空格可有可无（SpringBoot 也认作 Spring Boot）；
- 英文词后面跟版本号也算这个词（H21）：紧贴或隔一个空格，数字可以带小数点，前面可以有 `v`，末尾可以有 `.x`，例如"HTML5""Vue2.x""Python 3.10""Pythonv3.11""Photoshop 2024""Java8+"。版本号后面紧跟字母的不算，所以本身带数字的名字不会被拆开（"C4D"）；
- 较长的词优先（"Spring Boot"不会再被读成"Spring"）；
- 一份 JD 里同一个技能只记一次，按第一次出现的位置排序。

**追加自己的词条**：新建 `data/config/skills.json`（UTF-8），格式和内置词表相同。词条会加进同名分组；写一个新的分组键就是新分组（键只能用小写字母、数字、`-` 和 `_`）；`same_as` 里写自己的同义词组。

```json
{
  "version": 1,
  "groups": {
    "ops": {"terms": ["私域运营", "私域流量运营", "KOL投放"]},
    "game": {"label": "游戏", "terms": ["Unity", "关卡设计"]}
  },
  "same_as": [["私域运营", "私域流量运营"]]
}
```

- 只能追加，不能删除或移动内置词条：写了已有的词会被忽略；
- 同义词组里的词必须先写进某个分组的 `terms`（内置的也行），而且属于同一个分组；和内置的组有相同的词时，两组并成一组；
- 文件格式不对时 `jd parse` 和 `profile validate` 报错（退出码 2），不会只读一半；
- 用 `--data-dir` 或 `JOBSEARCH_CN_DATA_DIR` 换了数据目录时，读的是那个目录下的 `config/skills.json`。

## 局限

- 规则是保守的。单独的"本科"等学历词只从确认的标签行里补读，普通正文中的裸学历词仍需 Agent 或用户补全。
- 城市只认一份常见城市的固定列表。
- 标题只看"职位名称：…"、跳过开头"标签：值"行后的第一行，以及整页复制时前 30 行里带薪资的岗位名。这一行要含"实习""工程师""经理""专员""管培生""销售""编辑""策划"等岗位用词，才会被当作标题；其他写法留空，由 Agent 补全。
- 整页复制时，"工作地址"单独一行、地址写在下一行的，城市读不出来。
- 标签行从已识别标题后的页头区域查找，不受页面前 30 行限制；遇到正文、公司介绍、推荐职位的段落标题或句子就停止。没有识别到标题时，仅保留开头 30 行内的候选查找；标题本身的识别范围不变。
- 标签行至少三格且含"N天/周"。每格都得是认得的标签词：城市（可带"·区"或多个城市）、区县、"N天/周"、"N个月"、学历、经验、届别、岗位类型、薪资；竖线分隔的第一格可为公司名，其余格仍须是标签。未知标签或句子不能据此补读城市、裸学历和时长。空格分隔的行不读公司。
- 薪数只读和月薪写在同一行的"13薪"，写在"转正后"之后的不读。写在福利那一行的"13薪"也可能属于另一种待遇，规则不读，由 Agent 补全。
- 面试和到岗时间（M2-6c）：
  - 线上和现场面试分两行写、没有哪一行同时写到两种的，一律算 `mixed`（至少一轮要到现场），哪怕原文是让你选；"线上/线下面试"这类只用"/"连起来的，也算 `mixed`。宁可多提醒一次出行成本，由 Agent 按原文改成 `either`；
  - 面试城市只认常见城市列表里的城市；"面试地点：公司总部"这类写法会算现场面试，但读不出城市；
  - 到岗时间按年份推断，推错一年就会多出或漏掉冲突。JD 跨年发布、又没写发布日期时，导入日期离发布日期越远，越容易推错；需要时由 Agent 按原文改；
  - "11月前到岗"、只写了"一周内到岗"这类相对时间，留空由 Agent 按原文补。
- 学历和专业（H20）：
  - 学历对只认用"或""或者""/""、"连起来、前有"学历："或后有"及以上""学历""在读""毕业""均可"等词的；标签行里的"大专/本科"这类格子仍读不出；
  - 专业名只在明确要求毕业专业时才不算技能（见上表）；拿不准的一律照常读成技能，宁可多读一个技能，也不删掉真实的能力要求。"有统计学背景""统计学方向优先"这类不带"专业"的写法也照常读成技能，由 Agent 按原文判断。
- 技能按原文匹配，不看上下文：
  - 同义词各按原文写法记录，"K8s""Kubernetes"都写了就两个都记；评分时按 `same_as` 算作一个技能。没列进 `same_as` 的写法仍算不同的技能，评分时也不在技能之间推断：档案只写了 RAG、LangChain 时，JD 要的"大模型"仍是缺口（见 [match.md 的维度](match.md#维度)）；
  - 带版本号的写法读不出，例如"HTML5""CSS3""Vue3"：英文词后面紧跟数字就不算完整的词。需要时在自己的词表里补上这种写法，再用 `same_as` 并到原来的词；
  - 公司介绍里只去掉平台名，其他词照常读出，例如"我们深耕数据分析"会读出"数据分析"；"接口设计规范"这类技术写法也会读出"设计规范"；
  - 否定只认写在技能前面的词，"Python 不作要求"读不出；"不要求精通 Python"也会把 Python 去掉；
  - 读"任选其一"的口径：
    - 组里的技能照常记进 `requirements.skills`，评分时一组算一项（见 [match.md](match.md#任选其一的技能h16)）；
    - 只看同一分句（逗号、分号、句号、换行之间）里紧挨着的技能：技能之间只能是"、""/""或""或者"，技能后面可以带"语言""框架""软件""工具"。"Python 和 Java 其中之一"里有"和"，不成组；跨行、分条列出的选项（"任选其一：\n1. Python\n2. Java"）也读不出；
    - "任一""之一""至少一门"这类词要在技能前后 15 个字以内，中间不能有"和""及""与""并""是""为"，免得把"熟悉 Docker、K8s 及至少一种语言 Java、Go"里的 Docker、K8s 也算进去；
    - "均可""都可以"不算：它们也常用来说"都要会"；
    - "或"连起来、但其中有"/"的（"Python/SQL 或 Tableau"）整串算一组；
    - 几处选择有共同的技能时（含同义写法：Go 和 Golang），合成一组，每处的原文都记进出处："熟悉 Python 或 Java；熟悉 Java 或 Go"读成 `["Python", "Java", "Go"]`。组里保留 JD 用过的每种写法（"熟悉 Rust 或 Go；熟悉 Golang 或 Java"读成 `["Rust", "Go", "Golang", "Java"]`），评分时同义写法只算一个技能；
    - 词表里没有的技能读不出，组也就读不出，例如"PS 或 AI"：词表收的是 Photoshop、Illustrator。"PS"作为 Photoshop 的同义写法由 H18 补上；"AI"不收，它在 JD 里多指人工智能，只有设计岗位里才指 Illustrator，单看这个词分不清，这是已知局限。读漏、读错的组由 Agent 按原文补或改。
- 记录的 `id` 由 JD 内容决定（忽略空白和换行的差异），同一份 JD 重复导入会得到同一个 `id`，这是本地岗位库去重的第一依据（见 [jd-import.md](jd-import.md#去重与合并)）。
